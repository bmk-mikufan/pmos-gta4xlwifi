### 설치/부팅 (2026-07-12)

1. **recovery zip 방식 실패** — initramfs가 `findfs PARTLABEL=system` 실패
   - `INSTALL_PARTITION=system` → `userdata`(소문자) 로 변경
   - zip 내부 설치기 스크립트 수정: 서브파티션 생성 안 하고 sda32에 직접 ext4 포맷

2. **fastbootd 설치 성공** (LineageOS recovery 내장 fastbootd)
   - `fastboot flash boot boot.img` → OK
   - `fastboot flash userdata rootfs.ext4` → OK (sparse 청크 분할)

3. **초기 부팅 실패 원인:**
   - initramfs가 `pmOS_boot` 레이블을 못 찾아서 debug shell 진입
   - fstab이 비어있어서 initramfs가 부트 파티션 찾기 시도 → 실패
   - **해결:** fstab에 `LABEL=pmOS_root / ext4 defaults 0 0` 추가

4. **UI 설정:**
   - 처음: console → gta4xl과 동일한 UI 확인 요청
   - gta4xl = XFCE4 (X11, fbdev, wayland 불가)
   - neofetch, btop, plymouth 사전탑재
   - lightdm 비활성화 → tty 부팅 후 `startx`로 XFCE 실행

5. **최종 설치 방식:**
   - 수정된 recovery zip (서브파티션 없음) → `~/gta4xlwifi/pmos-samsung-gta4xlwifi.zip`
   - 또는 fastbootd로 직접 플래싱

  - 해결: 수동 설치

### S-BOOT DTB 문제와 해결
- **문제:** Samsung S-BOOT가 boot.img v2 header DTB 영역에서 일반 FDT (`0xD00DFEED`)를 인식 못 함
- **에러:** `[UFDT] DTB LOAD FAIL.` / `ERROR:[DTH] dt table header check Fail`
- **원인:** S-BOOT는 DT table header (`0xEDFE0DD0` / `0xD7B7AB1E` magic)를 기대
- **해결:** `mkdtboimg create --custom0=0x00000000 --custom1=0xff000000`으로 DTBO 포맷 생성 후 v2 header에 배치
- **v2 header 필드:** dtb_addr=0x10000000, dtb_size=26624

### 빌드 문제 해결
- `pmbootstrap zap -a` 후 빌드 환경 복구 필요
- `devicepkg-dev`, `clang`, `openssl-dev`, `linux-headers` 수동 설치 필요
- 커널 빌드 약 60-75분 소요
- `mkbootimg`의 `--dtb` 플래그가 v2 header DTB 필드를 설정하지 않음 → 수동 패치 필요

### USB DWC3 DTS (WIP)
- DWC3 controller: 0x13200000, PHY: 0x131d0000
- 호환 문자열: `samsung,exynos850-dwusb3` / `samsung,exynos850-usbdrd-phy`

### 알게 된 것
- **메인라이닝 원칙:** KISS — 최소 기능만, downstream 코드 복사 금지
- **chimac의 저장소가 정답** — 최대한 베끼고 최소만 수정
- gta4xlwifi DTS는 gta4xl과 거의 동일, 별도 생성 불필요
- Wi-Fi/Modem 차이는 DTS 수준이 아닌 드라이버 레벨에서 처리
- Samsung S-BOOT는 DTBO 포맷(`0xD7B7AB1E`)만 인식 — 일반 FDT는 거부
- boot.img의 v2 header DTB 영역은 mkdtboimg로 생성한 DTBO 이미지로 채워야 함
- uniLoader가 U-Boot보다 framebuffer 초기화에 더 적합함
- `CONFIG_BOOT_PRINTK_DELAY` 없으면 `boot_delay` 커널 파라미터 무시됨
- pstore/ramoops는 Samsung S-BOOT DRAM 리셋으로 데이터 보존 안 됨
- UFS 드라이버(`SCSI_UFS_EXYNOS`)와 PHY(`PHY_SAMSUNG_UFS`)는 mainline에 존재
- Exynos 9611 UFS 주소: 0x13520000 (추정, exynos7-ufs 호환)

## 2026-08-29: uniLoader 부팅 실패 (DT Load Fail) 근본원인 조사 및 __symbols__ 수정

### 문제
S-BOOT UFDT 단계에서 지속적으로 동일 오류:
```
ODIN MODE (DT Load Fail)
No node __symbols__ in main dtb.
ufdt overlay apply fail
[UFDT] DT Overlay FAIL.
```
u-boot.dtb로 wrap해도, 커스텀 DTBO 스텁으로 wrap해도 동일 오류 재현 (병렬 서브에이전트
3개로 git 히스토리/uniLoader 업스트림/last_kmsg 조사 → uniLoader 자체는 boot.img
v2-header dtb를 아예 읽지 않음(자체 임베드된 blob/dtb만 사용)을 소스 레벨로 확인,
DT Load Fail은 uniLoader와 무관하게 S-BOOT의 UFDT가 v2-header dtb를 처리하는
단계에서 발생).

### 근본원인 (확인됨)
`unpack_bootimg`으로 확인한 dtb_addr=0x0 문제는 `deviceinfo_flash_offset_dtb`를
"0x10000000"으로 바꾸는 것만으로 해결됨 (mkbootimg --dtb_offset은 정상 동작 —
이전 세션의 "mkbootimg 버그" 추정은 틀렸음, 실제로는 --dtb_offset을 안 넘겼던 것뿐).

그러나 dtb_addr을 고쳐도 동일 오류 지속. `dtc -I dtb -O dts <dtb> | grep __symbols__`로
직접 확인한 결과 u-boot.dtb, 메인라인 커널의 exynos9610-gta4xl.dtb **둘 다**
`__symbols__` 노드가 없음. 커널 dtb는 CONFIG_OF_OVERLAY=y로도 해결 안 됨 —
이건 런타임 오버레이 지원 심볼일 뿐, dtc -@ 여부와 무관 (scripts/Makefile.dtbs 직접
확인: `DTC_FLAGS += $(if $(filter ...,$(base-dtb-y)), -@)` — 커널 빌드 시스템의
"오버레이 base로 등록된 dtb"에만 자동으로 -@가 붙고, gta4xl dtb는 거기 해당 안 됨).

### 적용한 수정
`linux-samsung-exynos9610/APKBUILD`의 build()에 `DTC_FLAGS_<target-stem>` per-target
오버라이드로 강제 -@ 추가:
```sh
make ARCH="$_carch" LLVM=1 DTC_FLAGS_exynos9610-gta4xl=-@ dtbs
```
결과: exynos9610-gta4xl.dtb에 __symbols__ 생성 확인됨 (27048→42381 bytes).
`u-boot-exynos9610/APKBUILD`도 이 심볼 포함 dtb를 mkdtboimg로 wrap하도록 변경
(u-boot 자신의 dtb 대신 커널 apk에서 직접 tar로 추출 — pmb:cross-native라
makedepend로 aarch64 커널 패키지를 못 붙이므로).

### 결과: 여전히 실패
빌드한 boot.img에서 __symbols__ 존재를 dtc로 직접 재확인(1개 발견)했고
dtb_addr=0x10000000/dtb_size 정상, 크기도 파티션 이내(58MB) 확인 후 플래시.
리부팅 후 60초간 폴링 → `lsusb`가 계속 `04e8:685d` (Samsung Odin/Download 모드
USB descriptor)만 보임, adb/fastboot 둘 다 미검출. → __symbols__ 문제가 아니거나,
__symbols__만으로는 불충분 (dtbo 파티션 자체의 overlay fixup 내용이 이 main dtb의
심볼과 phandle이 안 맞을 가능성, 또는 완전히 다른 실패 지점).

### 확신도
- ✅ dtb_addr=0x0 → 0x10000000 수정이 유효했음 (deviceinfo만으로 충분, 수동 바이너리
  패치 불필요)
- ✅ __symbols__ 노드 부재가 실재했고 DTC_FLAGS_<stem>=-@ 로 해결 가능함을 확인
- ❌ __symbols__ 추가가 실제 부팅 성공의 충분조건인지는 미확인 (여전히 Odin 모드로
  fallback) — 시리얼/UART 없이는 정확한 새 실패 메시지 확인 불가

## 2026-08-30: reserved_memory 라벨 수정 + 진짜 uniLoader 페이로드 복구, 그래도 실패

### 문제 재현 (새 에러)
`__symbols__` 수정 이후 재부팅에서 다른 오류 확인됨 (사용자가 화면에서 직접 확인,
파일 캡처는 실패):
```
Couldn't find 'reserved_memory' symbol in main dtb
failed to perform fixups in overlay
ufdt overlay apply fail
[UFDT] DT Overlay FAIL.
```

### 원인 (확인됨)
dtbo 파티션의 오버레이(`fragment@0`/`fragment@50` 등)가 `&reserved_memory` phandle을
타겟팅하는데, 메인라인 dts(`0012-arm64-dts-exynos-Add-initial-support-for-the-Exynos9610.patch`의
`exynos9610.dtsi` reserved-memory 노드)에 라벨이 없어서 `__symbols__`에 항목이 없었음.
git으로 확인한 결과 이 라벨은 이 패치가 최초로 커밋된 7/27(c58a2e5)부터 계속 없었던
결함 — chimac v3 클럭 패치나 다른 변경과 무관, 원래부터 있던 gap.

### 적용한 수정 1: reserved_memory 라벨 추가
`0012-...Exynos9610.patch`의 `reserved-memory {` → `reserved_memory: reserved-memory {`
한 줄 수정 + APKBUILD 체크섬 갱신. 재빌드 후 dtc로 `__symbols__`와 `reserved_memory`
둘 다 확인됨.

### 적용한 수정 2: 진짜 uniLoader 페이로드 복구
`uniloader-exynos9610` APKBUILD가 처음부터(7/27) 빌드 불가능한 스켈레톤(git+ 소스,
SKIP 체크섬, 잘못된 설치 경로)이었음이 git으로 확인됨 — 이 세션 초반에 실수로 이
상태로 되돌아간 것. `APKBUILD.old` 백업에서 실제 작동했던 레시피(실제 tarball 소스,
올바른 설치 경로 `/usr/share/u-boot/gta4xl/uniloader.bin`)를 발견, 복원.

단 원래 레시피는 `/mnt/rootfs_<device>` 임시 마운트(pmbootstrap install 도중 ~90초만
존재)에 의존해서 매번 타이밍 경쟁으로 실패함. 최종 해결책:
- vmlinuz/dtb: 커널 apk에서 직접 tar 추출 (u-boot-exynos9610에서 이미 검증된 패턴)
- initramfs: mkinitfs를 독립 실행할 방법이 없어서(순환 의존성 — initramfs는 오직
  rootfs 조립 중에만 생성됨), 기존 device rootfs chroot에 mkinitfs/boot-deploy/커널
  모듈을 수동으로 채워넣고 `sudo chroot ... mkinitfs -d /tmp/out`로 1회 생성 후
  `gta4xlwifi.initramfs`로 uniloader-exynos9610 패키지에 정적 파일로 vendoring함
  (원래 git 저장소의 최초 스켈레톤도 로컬 파일 소스를 의도했던 것과 일치).

최종 빌드 검증: boot.img의 kernel 필드(51318784 bytes)가 uniloader.bin과 정확히
일치(진짜 uniLoader가 페이로드로 들어감 확인), dtb는 `mkdtboimg dump`로 실제
오프셋(64)/크기(42445) 찾아서 슬라이스 후 dtc로 `__symbols__`=1,
`reserved_memory` 라벨 둘 다 확인.

지금까지 중 가장 정확하게 검증된 빌드(진짜 uniLoader + 두 라벨 수정 완료)를 두 번

### last_kmsg로 원인 확인 시도 — 근본적으로 불가능하다는 결론
`/proc/last_kmsg`를 여러 번 다시 pull 받아 확인했으나 매번 무관한 과거 다운스트림
Android 부팅 로그만 나옴(strings로 dbmdx/fimc_is/sec_bat 등 확인, 리커버리 자체
부팅 로그로 판명). 원인: 이 데이터는 DRAM 고정 영역(0xf9d10000)에서 오는데, uniLoader
부팅 시도마다 S-BOOT가 그 전에 DRAM을 리셋함(기존에 문서화된 사실). 즉 메인라인
시도가 이 버퍼에 도달한 적이 원천적으로 없음 — **이 방법으로는 절대 메인라인 실패
원인을 못 본다.** `/cache/recovery/last_kmsg`도 recovery가 매번 자동 복사하는 것뿐이라
캐시를 지워도 소용없음.

### last_kmsg_final (2MB 완전 캡처) 분석 — 여전히 진짜 실패 로그는 못 얻음

Odin 하드리셋이 RAM 커널 로그를 깨뜨리는 문제를 사용자가 회피하는 방법을 찾아서
2MB 전체 캡처(`last_kmsg_final`)를 받았으나, 분석 결과 내용물은:
- **리커버리(다운스트림 Android 4.14.356) 부팅 2회, 둘 다 완전 성공** — ueventd/
  servicemanager까지 정상 진행, 크래시 없이 자발적 `reboot cmd: sw reset`으로 종료.
  패닉/Oops/워치독 리셋 전혀 없음 (전체 파일 grep으로 확인).
- Odin 재플래시 세션 1회 (`s5p_restart_handler ('N':ODIN_RESET)`)
- **가장 최근 시도(우리가 원했던 메인라인 테스트로 추정)**: `Starting kernel...`
  한 줄 찍히고 그 직후 파일이 끝남 — 커널의 첫 printk(`Booting Linux on physical
  CPU 0x0`, 보통 진입 즉시 출력됨)조차 전혀 없음.
- 파일 맨 앞의 비트 손상된 구간도 legible한 부분은 리커버리 부팅 패턴과 동일 —
  새로운 정보 없음 (ring buffer wrap 잔재로 추정).

**결론**: 이번에도 메인라인 커널 자체의 크래시/패닉 로그는 확보 못 함. 다만

**uniLoader가 커널로 점프하기 전에 멈췄을 가능성**을 시사함 (기존엔 DT/오버레이
쪽만 의심했으나, 이제 uniLoader 자체의 진입 주소/gta4xl_defconfig/임베드 blob
파싱도 의심 대상에 추가해야 함).

### 핵심 질문과 근본 해결
사용자 질문: "uniLoader를 쓰면 dtbo 종속성이 없어져야 하는 거 아니냐?" — 정확한
지적이었음. uniLoader 소스(https://github.com/ivoszbg/uniLoader.git)를 직접 클론해서
분석한 결과:
- `arch/aarch64/start.S`: 진입 즉시 x0 레지스터를 자기 자신의 내장 dtb 주소로
  덮어씀 — S-BOOT가 dtb/dtbo로 뭘 했든 uniLoader는 전혀 안 봄, 자체 임베드된
  `blob/dtb`만 사용 (링커 스크립트 `linker.lds.S` + Kconfig `DT_PATH`로 빌드 시
  바이너리에 직접 링크됨).
- 즉 **uniLoader 자체는 dtbo 오버레이 결과와 완전히 무관** — 사용자 가설이 맞았음.
- 다만 S-BOOT 자체의 UFDT 게이트(오버레이 적용 실패 시 uniLoader 진입점까지
  아예 못 감)는 우회 불가 — uniLoader 저장소 어디에도 대안 플래시 경로 없음
  (`grep -rniE "dtbo|heimdall|kexec|recovery|odin"` 전체 0건, 커밋 메시지에
  "uniLoader is loaded by S-Boot as an uncompressed Image"로 명시).
- **추가로 결정적인 발견**: gta4xl 보드용 uniLoader에는 UART 콘솔이 전혀 없음
  (`board-gta4xl.c`엔 simplefb만 등록, earlycon 미설정) — 즉 handoff 이후
  USB/kmsg로 아무것도 안 보이는 게 정상적인 상황일 수 있었음 (last_kmsg로는
  이 보드에서 uniLoader/커널 성공 여부를 원천적으로 판별 불가).

### 적용한 수정: 다운스트림 dtbo 대신 빈 오버레이
다운스트림 실 dtbo.img를 썼을 때 `Little Find DTBO Entry[1]`이 선택되면서
`Couldn't find 'dsim_0' symbol in main dtb`로 실패(디스플레이 컨트롤러 노드가
메인라인 dts에 아예 없어서 라벨 추가로 해결 불가능한 수준). 그래서 다운스트림
dtbo 의존을 완전히 버리고, **아무 fixup도 없는 최소 유효 DTBO 컨테이너**를 직접
생성:
```
/dts-v1/; /plugin/;
/ { fragment@0 { target-path = "/"; __overlay__ { }; }; };
```
`dtc -@`로 컴파일 → `mkdtboimg create --custom0=0x00000000 --custom1=0xff000000`로
wrap (140바이트 오버레이, 204바이트 dtbo.img) → `fastboot flash dtbo` →
`fastboot flash boot` (uniLoader+reserved_memory 라벨 수정 커널) → 재부팅.

... 7.2.0-rc1 #1-postmarketOS PREEMPT ...

### 남은 문제: 루트 파일시스템 마운트 실패 (완전히 다른, 훨씬 흔한 종류의 문제)

## 2026-08-30 (계속): initramfs 수정, dtbo 근본 해결, 워치독 확정, 클럭 v1 원복

하루 종일 이어진 세션. 아래는 위 시점 이후 전체 흐름을 시간순으로 요약.

### 1. initramfs `/init` 부재 문제 확정 및 수정
수동으로 mkinitfs를 fakeroot에서 돌려 만든 `gta4xlwifi.initramfs`(3.9MB)를 cpio로
까보니 `/init`, busybox 등 핵심 파일이 전부 빠진 빈 껍데기였음(fakeroot 구성 시
mkinitfs의 기본 hooks/dirs/files 패키지를 못 채웠던 게 원인). **해결**: 진짜
`pmbootstrap install`이 만든 13MB짜리 initramfs(`/mnt/rootfs_<device>/boot/initramfs`,
설치 도중에만 잠깐 마운트됨)를 그대로 복사해서 vendoring. 이걸로 처음으로 커널이
`Run /init as init process`를 지나 실제 유저스페이스까지 진입.

### 2. dtbo 종속성 근본 해결
사용자 질문("uniLoader면 dtbo 종속성 없어져야 하는 거 아니냐?")이 결정적이었음.
uniLoader 소스(`arch/aarch64/start.S`)를 직접 클론해서 확인한 결과, **uniLoader는
S-BOOT가 dtb/dtbo로 뭘 하든 완전히 무시하고 자기 자신의 컴파일 타임에 링크된
`blob/dtb`만 사용**함(x0 레지스터를 진입 즉시 덮어씀). 단, S-BOOT 자체의 UFDT
게이트(오버레이 적용 실패 시 아예 커널 진입 자체를 안 시킴)는 uniLoader와 무관하게
통과해야 함 — 우회 방법 없음.

다운스트림 실 dtbo.img를 썼더니 `Little Find DTBO Entry[1]`이 선택되면서
`Couldn't find 'dsim_0' symbol in main dtb`로 실패(디스플레이 컨트롤러 노드가
메인라인에 아예 없어서 라벨 추가로 해결 불가). **최종 해결**: 다운스트림 dtbo를
버리고, 아무 fixup도 없는 최소 유효 DTBO 컨테이너(빈 오버레이 fragment)를 직접
만들어서 사용. S-BOOT의 포맷 검사는 통과하고 고칠 것도 없어서 트리비얼하게 성공.
이제 `device-samsung-gta4xlwifi-mainline` 패키지의 `package()`가 이 최소 dtbo.img를
빌드 산출물로 직접 생성함 (postmarketOS deviceinfo엔 "dtbo 파티션" 개념이 없어서
`fastboot flash dtbo boot/dtbo.img`는 여전히 수동 스텝).

### 3. bootargs가 uniLoader에서 전혀 반영 안 되던 문제 확정
`pmos.debug-shell`, `boot_delay=100`을 `deviceinfo_kernel_cmdline`에 넣어도 커널에
전혀 안 들어감. 원인: **uniLoader가 쓰는 dtb(=자체 컴파일된 메인라인 커널 dtb)의
`/chosen/bootargs` 프로퍼티가 chimac의 원본 보드 DTS(`0013-...Samsung-Galaxy.patch`)에
`"earlycon=simplefb,... keep_bootcon"`으로 하드코딩돼 있었음.** deviceinfo의
커맨드라인 설정은 boot.img의 v2-header 필드에만 반영되는데, 그건 uniLoader가
아예 안 봄 (dtb와 마찬가지로 자기 dtb에 이미 박혀있는 값만 씀). **해결**: 이
DTS 소스의 `bootargs` 문자열을 직접 고쳐야 함 — 이후 `pmos.debug-shell`,
`initcall_debug`, `loglevel=8` 등이 정상 작동 확인됨.

### 4. 하드웨어 워치독 확정 및 수정
`boot_delay`+`initcall_debug`로 확보한 ramoops 로그에서 `Freeing initrd memory` 직후
매번 같은 지점에서 재부팅되는 패턴 확인. 다운스트림 소스(`exynos9610.dts`)에서
watchdog_cl0@0x10050000(exynos7-wdt 호환), watchdog_cl1@0x10060000 두 개를 확인,
메인라인에 이미 있는 `s3c2410_wdt` 드라이버(probe 시 `tmr_atboot=0`이면 무조건
정지시킴)로 둘 다 노드 추가 + `CONFIG_WATCHDOG`/`CONFIG_S3C2410_WATCHDOG` 활성화.
실제 dmesg로 둘 다 `watchdog inactive, reset disabled, irq disabled`로 정상 probe
확인됨. **그러나 워치독을 둘 다 껐는데도 정확히 같은 지점에서 재부팅이 지속** —
워치독은 원인이 아니었거나, 원인 중 하나였지만 유일한 원인은 아니었음.

### 5. ACPM/mbox 배제
새로 추가한 ACPM IPC/mailbox 드라이버가 의심됐으나(probe 코드에 SRAM readl()이
있고, 예전에 이 SRAM을 `/dev/mem`으로 읽다가 즉시 재부팅된 전례가 있어서), DT
노드를 `status="disabled"`로 완전히 꺼도 **완전히 동일한 오류, 동일한 로그**로
재현됨 → 확정적으로 배제.

### 6. genpd(전력관리) 배제
전체 트리에 power-domain provider 노드가 하나도 없어서 `genpd_power_off_unused()`가
순회할 대상 자체가 없음(로그의 해당 줄은 장식용) — 소스 레벨로 확정 배제.

### 7. `console-ramoops` vs `pmsg-ramoops`, `initcall_debug`로 최대한 확보
- ramoops의 `console-size`(512KB)는 우리가 받은 로그(~15KB)에 비해 훨씬 커서
  **용량 문제가 아님** — 그 지점 이후 진짜로 아무것도 안 찍힌 것.
- `setup_log()`가 `/dev/pmsg0`로도 로그를 보내려 시도하지만 `CONFIG_PSTORE_PMSG`가
  꺼져있어서 `/dev/pmsg0` 자체가 없음 — 이 경로로 더 볼 방법은 이번엔 막힘(커널
  재컴파일 필요, 다음 기회에 켤 것).
- `initcall_debug loglevel=8 ignore_loglevel`을 추가하니 로그가 `Run /init as init
  process`를 넘어 실제 유저스페이스 진행(`mount_proc_sys_dev()`의 `modprobe
  libcomposite` 성공, PID 97)까지 잡힘 — 역대 최고 진행 지점. 그 직후 화면 로고가
  다시 뜨는 완전한 하드 리셋 발생(사용자 직접 확인). `libcomposite` 로드는
  debug_shell()이나 USB gadget과 무관한, `/init` 최초 단계의 완전히 정상적인
  루틴(`mount_proc_sys_dev()`가 PMOS STAGE 1 echo보다도 먼저 실행)이라는 것도
  코드 레벨로 확인.

### 8. chimac 클럭 드라이버 v1 vs v3 조사 및 v1 원복
사용자가 "예전 github 저장소 기준으로는 debug shell까지 진입했다"고 기억 — 그
시점엔 ACPM/mbox/워치독 전부 없었으니, 실제 회귀 후보는 **8/28에 v1(Sep14
초안)에서 v3(7/22, LKML에 리뷰 올라간 버전)로 갱신한 클럭 드라이버**로 좁혀짐.
서브에이전트로 실제 diff 확인 결과:
- v1→v3에서 CMU_CPUCL1(빅 클러스터 클럭 도메인) 지원이 통째로 빠짐 — 근데 우리
  DTS의 cpu4-7 노드엔 애초에 clocks/opp-table가 없어서(PSCI로만 부팅) 이건
  **아무 기능적 영향 없음**, v1로 되돌려도 공짜로 되돌아옴.
- v2→v3 사이엔 DISPAUD 클럭 게이팅 레지스터 오프셋 버그 수정이 있었음 — 이건
  우리 프레임버퍼(simplefb, 부트로더가 이미 세팅)가 이 드라이버를 거치지 않을
  가능성이 높아서 실질적 손해 아닐 걸로 판단.
- v1에 우리 워치독이 의존하는 `CLK_GOUT_PERI_WDT_CLUSTER0/1_PCLK` 클럭 정의가
  이미 존재함을 확인(v3 전용 추가가 아니었음) — v1 원복해도 워치독 픽스는 안 깨짐.

**결론**: v1 원복은 리스크 대비 저비용 실험. git(`c58a2e5` 커밋)에서 v1 patch 3개
(CMU bindings, SYSREG bindings, clock-controller-driver) 복원 + DTS의 cpucl1
include 경로/clocks 프로퍼티 원복. v3는 `v3-backup/` 디렉토리에 보존.

### 인프라 문제 (기록 필요)
- **패치 파일에 직접 줄 삽입 시 unified diff hunk 헤더(`@@ -0,0 +1,N @@`)의
  N을 반드시 같이 갱신해야 함.** 안 하면 `patch`가 조용히(에러 없이) 뒷부분을
  잘라먹고, 그 결과가 한참 뒤 `dtc` 컴파일 시점에 전혀 관련 없어 보이는 문법
  오류로 나타나서 원인 추적이 매우 어려움. → 항상 로컬에서 전체 패치 시퀀스를
  더미 트리에 적용 + dtc까지 컴파일해보고 나서(수 초) pmbootstrap 전체 빌드(30분
  이상)를 돌릴 것.
- **체크섬은 반드시 `pmbootstrap checksum <pkg>`로 갱신.** 수동 sha512sum 계산 후
  깜빡하고 반영 안 하거나 오타 내는 실수가 이번 세션에만 여러 번 발생.
- **abuild는 매 빌드마다 srcdir를 완전히 새로 푼다** — 즉 파일 하나만 바꿔도
  캐시 이득이 거의 없어서(ccache가 개별 컴파일 유닛은 캐시하지만, 전체 빌드
  그래프를 다시 도는 오버헤드는 그대로) 커널 빌드는 항상 25~40분 걸림.
- **이 머신은 RAM 7.5GB인데 스왑 9.7GB까지 쓰고 있었음** — 커널 빌드에 `-j$(nproc)`
  (12)를 주니 시스템이 맛이 가면서 빌드가 죽음(추정: OOM/스래싱). `-j4`로 낮춰서
  해결. 이 머신에서 커널 빌드 시 nproc 그대로 쓰지 말 것.
- **세션이 길어진 이후 `run_in_background` bash 태스크가 지속시간과 무관하게
  반복적으로 강제 종료됨** (커널 빌드든 20초짜리 uniLoader 빌드든 동일하게 killed).
  `nohup ... & disown`으로 완전히 분리한 프로세스 + Monitor로 로그 파일 폴링하는
  방식으로 우회 — 이후 전부 안정적으로 완료됨.

### 최종 확신도
- ✅ dtbo 종속성 제거, bootargs 하드코딩 문제, initramfs `/init` 부재 — 전부 확정
  원인 및 수정 완료, 재현 검증됨
- ✅ 워치독 CL0/CL1 probe 성공 확정 (dmesg 직접 확인) — 그러나 이것만으로 재부팅이
  해결되지 않음이 확정됨
- ✅ ACPM/mbox, genpd — 재부팅 원인에서 확정적으로 배제
- 🟡 클럭 v3 드라이버가 진짜 원인이라는 것은 아직 추정
- ❌ **v1 원복 테스트 결과 미확인** — 빌드/설치/플래시까지는 전부 완료했으나
  (커널 v1 클럭 + 워치독 CL0/CL1 + reserved_memory + 최소 dtbo + `initcall_debug
  loglevel=8 ignore_loglevel` bootargs, boot_delay는 이번엔 자동 진행이라 제외),
  플래시 직후 세션/환경이 한 번 리셋되면서(`/tmp` 스크래치패드 소실, 다행히
  `~/.local/var/pmbootstrap`의 빌드된 apk들은 생존) 재부팅 후 기기가 USB에서
  완전히 사라짐(Odin 모드조차 안 뜸) — 사용자가 외출 중이라 물리 확인 불가.
  **다음 세션에서 가장 먼저 할 일: 기기 전원/연결 확인 후 이미 플래시된 v1
  클럭 빌드로 재부팅 테스트, 안 되면 `pmbootstrap install --zap`으로 재구성
  (이미 빌드된 apk 재사용, 재컴파일 불필요) 후 재플래시.**

### 인프라 교훈 추가
- **이 환경은 세션이 오래 지속되면 `/tmp` 스크래치패드와 활성 마운트가 예고 없이
  초기화될 수 있음** (VM/컨테이너 재시작 추정). `~/.local/var/pmbootstrap`의
  빌드 산출물(apk)과 `~/.local/var/pmbootstrap/cache_git/pmaports`의 소스 변경은
  살아남으므로, 중요한 산출물은 항상 홈 디렉토리 기준 영구 경로에 있다고 가정하고
  `/tmp` 경로는 언제든 새로 만들어질 수 있다고 전제할 것.
- USB passthrough도 세션 경계에서 끊길 수 있음 — 재연결 후 `adb`/`fastboot`
  데몬이 자동으로 재시작되는 것도 확인됨(`adb devices`가 "daemon not running;
  starting now" 출력).

## 2026-09-06: 클럭 v1 결과 확정 — 원인 아님

형님이 v1 클럭 빌드로 실기기 테스트한 결과 **v1도 동일하게 재부팅**한다고 확인해 줬다.
따라서 chimac clocks v3 ↔ v1 차이는 이 하드 리셋의 원인이 아니다. (v3 백업은
`packages/linux-samsung-exynos9610/v3-backup/`에 그대로 둔다.)

이로써 현재까지 배제된 것: 워치독 단독, ACPM/mbox 드라이버, genpd, dtbo/bootargs 전달,
initramfs `/init` 누락, 그리고 clocks v1/v3.

### 이번에 정리한 것
- 저장소를 새 에이전트가 그대로 이어받을 수 있게 재구성했다:
  `HANDOFF.md`(인수인계 요약), `CLAUDE.md`, `.claude/{skills,agents}`,
  `docs/local/`(hardware/upstream/workflow/findings/wiki), `logs/`(실기기 로그) 전부 커밋.
- 대용량 바이너리(펌웨어 zip 492MB, recovery.img 71MB, samloader 바이너리)는
  GitHub 용량 문제로 제외했다. 필요하면 로컬 `~/gta4xlwifi/`에 그대로 있다.

### 로그 재분석에서 새로 알게 된 것
`logs/console-ramoops-0.log`의 cmdline에 `boot_delay=30`이 들어 있다. printk 한 줄마다
30ms를 넣으므로 4018줄 × 30ms ≈ 120초가 순수 지연이다. **로그의 132초는 실제 부팅 시간이
아니라 ~12초짜리 부팅이 늘어난 값**이다. 지금 DTS의 bootargs에는 `boot_delay`가 없으므로
현재 빌드는 ~10초 만에 `/init`에 도달한다.

이 때문에 아직 못 가른 것이 하나 있다: 리셋이 **`/init` 도달이라는 사건** 때문인지, 아니면
**전원 인가 후 ~133초라는 절대 시각**에 외부 감시자가 때리는 것인지. 지금 플래시된 v1 빌드의
`console-ramoops-0`를 한 번만 뽑으면 마지막 타임스탬프만 보고 즉시 갈린다. 다음 세션의
최우선 작업이다. 자세한 절차는 `HANDOFF.md` 6장 (A).

### 새로 세운 유력 가설
APM 코어에서 도는 ACPM 펌웨어가 AP 생존을 감시하고, 다운스트림처럼 주기적 핑이 없으면
SoC를 리셋한다는 것. 앞서 한 "리눅스 ACPM 드라이버 비활성화" 실험은 이 가설을 **반증하지
못한다** — 감시자는 APM 펌웨어 쪽이라 리눅스가 뭘 하든 계속 돌기 때문이다. 위 (A) 실험이
"고정 타임아웃" 쪽으로 나오면 이 가설이 유력해진다.

### reserved-memory 누락 발견 (2026-09-06) — 현재 1순위 가설

다운스트림 커널 소스(`arch/arm64/boot/dts/exynos/exynos9610-rmem.dtsi`, pmbootstrap
distfiles 캐시에 이미 받아져 있었다)와 실기기 `last_kmsg`의 `OF: reserved mem:` 줄을
대조했다. 메인라인 DTS는 예약 영역이 abox / framebuffer / ramoops 세 개뿐인데,
다운스트림은 20개 가까이 예약한다. 그중 메인라인이 "쓸 수 있는 RAM"이라고 선언한 구간
안에 들어와 있는 것들:

| 영역 | 주소 | 용도 |
|---|---|---|
| `sec_debug_magic` | 0x80000000 +0x1000 | 부트로더 리부팅 사유 매직 |
| `seclog` | 0xC0000000 +0x80000 | **EL3 보안 모니터 로그 버퍼** |
| `modem_if` | 0xED000000 +0x8A00000 | CP(모뎀) |
| `cp_ram_logging` | 0xF5A00000 +0x1E00000 | CP 로그 |
| debug-snapshot | 0xF9000000 ~ 0xFA710000 | DSS (header/log_kernel/.../kevents) |
| `gnss_if` | 0xFB000000 +0x800000 | GNSS 코프로세서 |
| `chub_rmem` | 0xFD000000 +0x80000 | CHUB 센서허브 펌웨어 RAM |

DSS 주소는 `include/dt-bindings/soc/samsung/debug-snapshot-table.h`의
`DSS_START_ADDR=0xF9000000` + 오프셋 누적으로 계산했다. 계산해 보니
`log_pstore` 슬롯이 정확히 **0xF9D10000 +2MB** — 지금 ramoops로 쓰는 그 주소다.
ramoops 배치는 그러니까 우연이 아니라 맞게 골라진 것이다.

결정적인 부분: 메인라인 부팅 로그의
`software IO TLB: mapped [mem 0x00000000fa000000-0x00000000fe000000]` — 64MB SWIOTLB
바운스 버퍼가 **DSS kevents(0xF9F10000~0xFA710000) + gnss_if + chub_rmem 위에 그대로
얹혀 있다.** CHUB/GNSS/APM 코프로세서는 S-BOOT가 켜 둔 상태로 리눅스와 독립적으로 계속
돈다. 서로의 메모리를 덮어쓰면 oops 한 줄 없이 SoC가 통째로 리셋된다 — 지금 증상과
정확히 일치하고, 지금까지 드라이버를 하나씩 끄는 실험이 전부 안 먹힌 이유도 설명된다.

조치: `0012-...-Exynos9610.patch`의 `reserved-memory`에 위 영역을 `no-map`으로 추가.
DSS는 ramoops 슬롯을 비켜 두 덩이(0xf9000000+0xd10000, 0xf9f10000+0x800000)로 쪼갰다.
패치 16개 적용 + `clang -E` + `dtc -@` 드라이런까지 통과 ✅. 체크섬은
`pmbootstrap checksum`으로 재생성. **실기기 검증은 아직 안 했다** — 기기가 연결돼 있지 않다.

### chimac clocks v3로 복귀 (2026-09-06)

v1/v3 어느 쪽이든 동일하게 리부팅하므로 클럭 버전은 원인이 아니다. 그렇다면 v1에 남아
있을 이유가 없다 — v3가 LKML에 올라가 리뷰된 버전이고, v2→v3에서 고쳐진 DISPAUD 클럭
게이팅 레지스터 오프셋 버그도 들어 있다. 상류와 갈라진 채로 두는 게 부채다. 그래서 v3로
되돌렸다 (0005/0006/0009 + 0012의 두 줄: 헤더 이름 `samsung,exynos9610-cmu.h`,
`sysreg_cpucl1`의 clocks 제거). v1은 `v1-backup/`에 보관.

`CLK_GOUT_CPUCL1_SYSREG_PCLK`가 v3 헤더에 존재하지 않는 것을 확인했다(grep 카운트 0) —
v3가 CMU_CPUCL1 도메인을 통째로 뺐다는 사실 재확인이고, `sysreg_cpucl1`의 clocks를
주석 처리한 것이 맞는 조치였다. DTS는 cpu4-7에 clocks/opp-table/cpufreq를 아예 안 붙이고
PSCI로만 부팅하므로 CMU_CPUCL1이 없어도 관측되는 영향은 없다.

검증: 패치 16개 적용 + `clang -E` + `dtc -@` 통과, `no-map` 예약 영역 10개 확인.

### 파티션 크기 실측 + 빌드 파이프라인 개선 (2026-09-06)

기기를 fastbootd로 연결해서 드디어 파티션 크기를 실측했다:

```
fastboot getvar partition-size:boot  -> 0x3B00000 = 61,865,984 B = 59.0 MiB
fastboot getvar partition-size:dtbo  -> 0x800000  = 8.0 MiB
```

**추측하던 64 MiB가 아니라 59.0 MiB다.** 다이어트 이전 boot.img가 57.5 MiB였으니
여유가 1.47 MiB밖에 없었다는 뜻이다. `CONFIG_FUNCTION_TRACER`를 켰다면 Image가
2~3MB 늘어 파티션을 넘겨서 플래시 자체가 실패했을 것이다. 앞서 ftrace를 뺀 판단이
결과적으로 맞았지만, 그때 근거로 삼은 "64MiB, 여유 ~6.8MB"라는 추정은 틀렸다 —
실제 여유는 그 1/4 수준이었다.

config 다이어트 결과 (arm64 defconfig가 켜던 SoC 벤더 플랫폼 53개 중 EXYNOS만 남김):

| | 이전 | 이후 |
|---|---|---|
| 활성 심볼 | 4639 | 2716 (-41%) |
| 오브젝트 | ~20000 | 7147 (-64%) |
| `Image` | ~46 MB | 29.4 MB |
| 커널 apk | 73.9 MB | 36.5 MB |
| 빌드 시간 | 2~3시간(콜드) | 30분 29초 |

증분 빌드 경로도 만들었다 (`scripts/ksetup.sh` + `scripts/kbuild.sh`). pmbootstrap의
`helpers/envkernel.sh`와 같은 원리로 커널 트리를 네이티브 chroot에 bind-mount하는데,
envkernel.sh는 gcc 크로스컴파일러를 하드코딩하고 이 커널은 clang/lld로 빌드하므로 make를
직접 호출한다. DTS만 고치면 `kbuild.sh dtbs`로 수 초, `pmbootstrap build --envkernel`
포장이 10초다.

포장 단계에서 `ERROR: Unable to open root`로 막혔는데, APKBUILD에 `options=`가 아예
없던 게 원인이었다. abuild가 마지막에 aarch64 루트를 상대로 의존성 추적을 하는데
envkernel 경로는 네이티브 x86_64 chroot에서 돌아 그런 루트가 없다. 상류 pmaports 커널
APKBUILD들이 전부 `!tracedeps`를 다는 이유다.

또 `pmbootstrap install`은 rootfs 계정 비밀번호를 대화형으로 물어서 비대화형 실행에서
죽는다. `--password`를 줘야 한다.

다이어트 검증 중에 기존 버그도 하나 나왔다: `PHY_EXYNOS5_USBDRD`가 `=m`이었다.
`depends on TYPEC || !TYPEC`인데 `TYPEC=m`이라 모듈로 끌려내려간 것으로, 다이어트
이전부터 그랬다. USB가 올라와야 할 시점에 modprobe할 rootfs가 없으므로 `TYPEC=y`로 고정.
